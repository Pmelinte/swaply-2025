## 1. Scope

This unit verifies and, where necessary, remediates the V1-09 privacy authority boundary for:

- GDPR data export;
- account-deletion request semantics and retention disclosure;
- exact versus approximate location;
- private conversations and messages;
- legacy and canonical token/Swapleni ledger data.

It does not declare Privacy sign-off or V1-09 closure by itself.

## 3. GDPR export — confirmed defect and remediation

### Before

`GET /api/gdpr/export` exported only a subset of the data exposed by the product contract and Account UI. In particular, it omitted conversations/messages and token ledgers. It also selected the non-existent Production column `gdpr_requests.completed_at`, which could cause export preparation to fail.

### After

The canonical download now includes authenticated-account metadata plus:

- profile;
- owned items;
- notifications;
- swap intents;
- canonical swaps where the user is a participant;
- conversations where the user is a participant;
- messages sent or received by the user;
- legacy `user_tokens`;
- canonical `swapleni_accounts` and `swapleni_ledger`;
- GDPR request history using the real `processed_at` Production column.

All reads remain server-side under the authenticated user's resolved ID. The endpoint does not trust a user ID supplied by the client.

**Predictive verdict:** `REMEDIATED / CI REQUIRED`.

## 4. Account deletion and retention — confirmed semantic defect and remediation

### Before

The active Profile UI used a client state helper that directly deleted only:

- owned items;
- notifications;
- profile row;

and then signed the user out. That was not a complete account erasure and could conflict with current relational integrity and retention obligations.

Separately, `/api/gdpr/delete` already provided the correct request boundary: authenticated + CSRF-protected creation of a pending deletion request in `gdpr_requests`. The route explicitly does not claim to perform immediate physical deletion.

### After

The active Profile account-deletion UI now routes through `/api/gdpr/delete`. It signs the user out only after the server accepts the deletion request. A failed request is surfaced as a failure rather than silently clearing local state.

The public Privacy retention disclosure now states that deletion requests are processed within 30 days, while records needed for overriding legal, security, fraud-prevention, dispute-resolution, accounting or integrity purposes may be retained in restricted form only as long as required. Other personal data is deleted or anonymized.

This wording matches the observed Production model, where several authority/evidence tables intentionally use restrictive foreign-key semantics rather than unconditional cascading deletion.

**Important boundary:** this unit does not claim that an automated deletion worker exists. The request-processing workflow remains an operational/legal follow-up item until separately proven.

**Predictive verdict:** `REQUEST AUTHORITY REMEDIATED / PHYSICAL PROCESSING NOT YET SIGNED OFF`.

## 5. Exact versus approximate location — replay result

Production and repository evidence show two distinct location layers:

1. exact domain-listing location is stored in `domain_listing_private_data.exact_location`;
2. public property coordinates are constrained by the canonical create authority to at most two decimal places.

The private table is RLS-protected for the owner and public/anonymous access is revoked. The public property-detail projection deliberately excludes raw `lat`, `lon` and address fields and emits only public location labels such as city/region/country.

The canonical domain creation authority rejects public latitude or longitude with precision greater than two decimal places with `Public coordinates must be approximate.`

`matching_items_v1` may contain the public property coordinate pair used for matching, but those coordinates are constrained by the same persistence authority to the approximate public precision. The exact coordinate payload remains in the private table.

**Replay verdict:** `PASS` for the current repository/Production authority model, subject to cumulative final replay.

## 6. Private conversations and messages — replay result

Live Supabase policies and repository migrations confirm:

- conversation SELECT is participant-bound (`auth.uid()` in `participant_ids`);
- message SELECT is sender/recipient-bound;
- message INSERT requires the authenticated sender and a recipient who belongs to the legitimate two-person conversation;
- operational message UPDATE is sender/recipient-bound;
- direct message DELETE is revoked from authenticated and anonymous roles.

The GDPR export uses service authority only after resolving the authenticated user and filters messages to rows where that user is sender or recipient.

**Replay verdict:** `PASS` for current authority, subject to cumulative final replay.

## 7. Retention implications discovered

Read-only Production inspection shows that some evidence/authority records reference `auth.users` with restrictive deletion semantics, including dispute, event-transfer, service-delivery, Story, swap authority/effect and Swapleni records. This is evidence that a correct deletion process cannot be represented by the former client-side three-table delete.

V1-09 Legal/Privacy closure must preserve a documented policy for deletion, anonymisation and justified retention rather than forcing destructive cascades that would invalidate dispute, ledger or security evidence.
