# Train E / E4.5 — Webhook Authority & Reconciliation

## Scope

E4.5 defines the canonical authority boundary for payment-provider webhooks and reconciliation. It does not activate a real payment provider and does not migrate the legacy Stripe or PayPal routes.

## Contract

A provider event may affect a service payment order only when:

1. the provider-specific signature has been verified server-side;
2. the provider event ID and SHA-256 payload digest are valid;
3. the event has been inserted into the server-only ledger;
4. the `(provider_id, provider_event_id)` uniqueness gate accepts it;
5. the event is not stale relative to a previously applied higher-priority event;
6. the transition is applied exactly once.

Invalid signatures fail closed and produce no payment side effect.

## Event ordering

Provider events may arrive late or out of order. Canonical priority prevents a stale `payment-pending` or `payment-failed` event from overwriting a confirmed payment or refund.

## Retry and dead-letter

Processing failures move to `retry-pending` with a bounded attempt counter and explicit `next_attempt_at`. Events reaching the maximum attempt count move to `dead-letter` for operator review. Replaying an already processed or ignored event returns the existing result and does not repeat effects.

## Reconciliation

Periodic provider-to-Swaply reconciliation compares the provider status with `service_payment_orders.status`.

- matching state: no action;
- provider-confirmed mismatch: apply the provider status through server-side authority;
- locally cancelled but provider-paid mismatch: manual review, never silent overwrite.

Each run and per-order decision are retained as immutable audit evidence.

## Legacy findings

The repository already contains Stripe and PayPal webhook handlers. They are not yet the E4.5 canonical implementation and are not activated or changed by this batch. A later integration batch must adapt them to this authority contract before any Production payment activation.

## Safety boundary

- no real checkout or charge;
- no provider secret added;
- no Production webhook endpoint activated;
- no card data stored;
- no wallet, credit or escrow balance;
- no browser writes to webhook or reconciliation tables;
- the swap itself remains free.
